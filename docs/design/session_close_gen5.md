# Session close, generation 5 — error taxonomy, the supervisor failure mode, and three standing rules

Provenance tags: **[M]** measured in this repository in this pass, with the artefact cited beside
it; **[L]** read from the project's own record — claim ledger, decisions, or an artefact a prior
pass banked; **[R]** relayed from the supervisor seat, unverified; **[UNVERIFIED]** believed here
with no means available to check it. This document is about a seat that spent a whole session
generating fluent, unverified specifics about project state, so it is placed under the same rule it
describes: every number below carries a tag, and a number in a brief that carries none should be
read as a hypothesis rather than an input.

## 1. The error taxonomy

The counts are the owner's tally from the session record, not a fresh count of anything [L]. They
are kept in the table exactly as given, and the representative examples are the ones that were
noticed, not a survey.

| Class | Count | One representative example | What it cost | Caught or not |
|---|---|---|---|---|
| Failed hypotheses about the root cause | ~12 | "the de-stagger rule explains the H ladder discrepancy" | a dispatch spent on a cause that was not there | usually after the dispatch, by measurement |
| Specification defects written into build briefs | ~11 | a brief naming the wrong file for the station fit | work correctly done against the wrong target | sometimes only when the deliverable could not be scored |
| False claims about project state | ~18 | `emfit/modal.py` described as absent from the repository | a stale ledger row; planning treated a working module as a gap | yes — by artefact, never by re-reading prose |
| Arithmetic and magnitude-estimate slips | 2 | 1.5 GB predicted, 2377.1 MB measured [L] | a resource plan off by more than 50 % | yes, on measurement |

**Failed hypotheses, about twelve.** Guessing *what* was broken was wrong more often than it was
right. The named cases are the H de-stagger hypothesis, the "split" hypothesis, the
epsilon-weighting direction, which was assumed backwards, "the worst rung is the problem", and "the
station fit is the culprit". Each was a plausible physical story and each cost a dispatch before
measurement could rule it out. The cost is not the measurement that refuted it — that measurement
usually carried information — but the dispatch that was framed around a cause that was not there, so
the deliverable could only ever be "no". Caught mostly by measurement, at the price of the dispatch.

**Specification defects, about eleven.** A brief asking for something unmeasurable, a brief naming
the wrong file or the wrong API, a brief freezing a criterion before the quantity in it had been
shown to be measurable at all. These are the failures that do not look like failures while they are
being written: they read as rigour. Their cost is work correctly done against the wrong target,
which is more expensive than work done badly, because nothing in the result announces the error.
They were sometimes caught only when the deliverable arrived and could not be scored.

**False claims about project state, about eighteen.** This is the worst class and the one the reader
of any of these documents is most exposed to. The representative case is `emfit/modal.py`:
repeatedly described as absent from the repository, including in a claim-ledger row recorded at the
strongest evidence grade, while the file was committed and 935 lines long [M, `wc -l emfit/modal.py`
= 935 in this tree]. The cost is a stale ledger row, and downstream planning that budgeted to build
a module that already worked. This class was caught every time by an artefact — a grep, an import
probe, a line count — and never once by re-reading prose, which reproduced the error faithfully each
time it was consulted.

**Arithmetic and magnitude-estimate slips, two.** The first was a 1.5 GB memory estimate against a
measured 2377.1 MB [L], a resource plan wrong by more than half. The second was conflating a guard's
*verdict* — its pass/fail judgement about a configuration — with a *ceiling*, the resource limit it
was being compared against, and reporting the two as one number. Both are cheap to make and
expensive to inherit, and the second is a category error of the same species as the
index-versus-quantity confusion diagnosed in section 2.

The taxonomy is not a confession. It is a map of where this seat's output is likely to be wrong, so
that a reader can discount it where it is weakest instead of discounting all of it evenly.

## 2. The supervisor failure mode

Read this section twice.

The supervisor seat has no file access. It cannot list a directory, open a file, run a command, or
check that a path exists. Everything it says about the state of the project is either relayed to it
by someone with access or generated by it from nothing, and the two are indistinguishable in its own
prose.

Generated specifics are fluent. A path that does not exist, a line count that was never measured, an
API name that was guessed, a test that was never written — all of these come out in the same
register as a number that was actually measured, with the same confident phrasing and the same
apparent precision. The failure is not lying. It is producing the shape of a verified fact out of no
evidence, which is worse for a reader, because the shape is exactly what a reader uses to decide
whether to check.

The rule that follows is narrow and does not reduce the seat's usefulness. **Physics reasoning is
yours.** Reasoning from Maxwell's equations about what a result must look like, what a discrepancy
implies, which of two explanations is dimensionally or variationally admissible — that is within
this seat's competence and should be trusted as such. **Project-state claims must be relayed or
verified.** What is in a file, who calls a function, how many lines it has, whether a test exists,
which module imports which — none of that can be reasoned to, and none of it may be asserted without
a tag that says where it came from.

A number in a brief with no provenance tag is unreliable, and the unreliability is silent. Treat an
untagged number as a hypothesis and not as an input. The cost of asking for it is one round trip.
The cost of not asking is a dispatch, and occasionally a ledger row that survives for weeks.

The worst instance deserves to be stated plainly, without softening. It is fabricating a *cause* for
an observed anomaly instead of saying "I don't know". An observation with a wrong explanation is
worse than an observation with none, because the explanation terminates the search: nobody
investigates further into a quantity that has already been explained. The correct output is the
anomaly plus explicit ignorance, and the second half is not a failure of the job.

## 3. Three standing rules

1. **Standing adversarial review before any criterion freeze.** No acceptance criterion is frozen
until a reviewer whose assigned job is to attack it has had its pass. A criterion frozen while it is
still arguable does not then get repaired when it is found wanting; it gets defended, because by
then a dispatch has been spent producing a number against it.
2. **Two questions at the head of every build brief.** First, *what already exists?* — which on this
project would have prevented rebuilding a committed module of 935 lines [M]. Second, *what has not
been varied?* — the highest-value question in the method, for the reason given in section 5.
3. **Provenance tags on every number in every brief and document**, in the four-tag scheme of the
heading: measured, read, relayed, unverified. The tags are not bookkeeping. They are the only
mechanism by which a reader without file access can tell which of the seat's confident sentences to
believe.

## 4. What worked

**The analytic anchor.** An exact reference solution found the nullspace starvation that internal
consistency checking could not. Internal checks confirm that a number is stable and reproducible;
they cannot tell you it is the wrong number. Only an independent reference can, which is why the
anchor was worth building before the ladder was worth sweeping.

**Artefact-wins.** The artefact beat the prose every time, without exception, and it is what caught
all eighteen project-state errors. The practice that matters is not the principle but the reflex:
any claim about the tree is settled by a grep or an import probe, immediately, rather than by
finding the most recent sentence that asserts it.

**Killing R instead of chasing it.** When the extracted quantity was found to be wrong, the move
that worked was to stop reporting it rather than to refine it. A wrong number that is being improved
stays in circulation and keeps being quoted; a number that is withdrawn stops costing anything.
Removing a bad quantity from the record was cheaper than any amount of correction applied to it.

**Refusing to freeze the pairing rule while seven attacks were still open [L].** A preregistration that
bends under pressure is worse than no preregistration, because it borrows the authority of a
commitment without carrying the constraint. Holding the rule open until the attacks were answered —
or the rule retired — was the right trade even though it delayed the freeze.

**Retiring the deflated path on scope, not repairing it.** A method that is valid only where the
normal field vanishes exactly does not need to be repaired; it needs a stated boundary and a
different method on the other side of it. Recognising that the boundary was the finding, rather than
a defect to be fixed, saved work that would have been spent making an inapplicable method
applicable.

**The admissibility guards rejecting all sixteen junk modes at h = 0.2** [L]. A guard that rejects
is worth more than a guard that ranks. Ranking moves the problem into a threshold that somebody will
later tune; rejection removes the modes from the candidate set and leaves nothing to tune.

## 5. What did not work

Hypotheses about *what* was broken were wrong more often than right, and this is the same
observation as section 1 seen from the other side: twelve failures, all of them guesses at a cause.

What worked was varying what had not been varied. Stated as a habit, it is the single most useful
thing in this record: the question is not "what is probably broken?" but "what have we never
changed?" The failures are all guesses at a cause; the successes are all cases of changing an
unvaried thing and watching what moved. The second question has an answer that the world supplies,
and the first has an answer that the seat supplies.

One caution about the catch rate. Parallel dispatch would lower it. The near-perfect catch on
project-state errors is partly an artefact of working one dispatch at a time, where each returned
artefact could be checked against the last, and the contradiction became visible in the checking
rather than in the asking. That is a property of the working pattern and not a property of the seat;
it should not be read as evidence that the seat's project-state claims are reliable.

## 6. What was never done: the coherence pass

This document is the first half of the close-out. It names the errors. The second half — re-reading
the whole design record against the tree and the banked artefacts, and repairing every row that no
longer matches — was never done, and it is the correct next work after the pipeline map.

The reason it matters is already visible in the map. `docs/design/pipeline_map.md` [M] records at
least one stale claim-ledger row, `C26` at evidence grade E1, which asserts that `emfit/modal.py` is
absent from the repository and exists only in `.scratch/`. In this tree the file is committed at 935
lines and imported in four places [M, both the line count and the import count are recorded in that
map's finding (vii) and its section on ledger-versus-tree contradictions]. One instance of a class
is evidence of the class, not an isolated typo: a ledger that has drifted once has drifted wherever
nothing forced it to be re-read, and the tags in the ledger do not decay when the tree moves
underneath them.

## 7. What to distrust about this document

- The counts are a tally kept by the seat that is being criticised, so they are a lower bound and probably a loose one.
- The examples are the ones that were noticed. Every class here certainly contains unnoticed members, and the unnoticed ones are systematically the ones that cost nothing visible.
- Every claim about the tree in this document is only as good as its tag. Where there is an [M] there is an artefact; where there is an [L] the figure is trusted as recorded and was not re-measured in this pass; where there is no tag there is nothing.
- This was written by the same seat whose central failure it describes. That is a conflict of interest the reader should hold against it, including against its account of what worked.
