**How to read a row.** Seven fields, always in this order: **what** it is (one sentence) / **where** the path and the symbol that identifies it / **state** one of ACTIVE, SHELVED, DESIGNED-ONLY, DEAD, UNLANDED, UNKNOWN / **why** the token that decides the state, quoted / **would change** the un-shelving condition, or "not stated" / **verified** the last commit subject that touched the path, with the commit's short hash, and the file's mtime in this working copy.

State vocabulary: **ACTIVE** = something exercises it (a test, a front end, the CLI) and its last subject describes work on it. **SHELVED** = it exists and works, and a document says its result was stopped, superseded in standing, or weaker than a claim made about it. **DESIGNED-ONLY** = prose or a preregistration names it; no implementation token. **DEAD** = superseded and unreferenced by any live path. **UNLANDED** = present in a working tree with no committed blob. **UNKNOWN** = the sweep could not decide, and the missing fact is named.

No line numbers appear below, by the rule in `d58_acceptance.md` section 0. Every citation is path + symbol, or path + quoted token. A quoted token is greppable; a line number would not survive the next insertion, and this map has to survive until someone re-measures it.

## How a row goes stale

**A row is stale by definition** if, at the moment it is read, the last commit subject that touched its path differs from the subject recorded in the row, or if the path no longer exists or has become untracked. No reviewer, no threshold, no judgement: the comparison either matches or it does not.

**Exactly how to check one row:** take the path from the row's *where* field and run the per-path log query the repository's tooling provides (`git log -1 --format=%s -- <path>`). Compare the first line with the row's *verified* subject. For a directory-shaped row, use the directory; for a file-shaped row, use the file. A directory row and a file row inside it will disagree the moment any file in that directory changes, which is why every row above names the narrowest path that identifies it.

**What a stale row looks like on the page.** It is not deleted and it is not quietly re-measured as if it had always said the new thing. It gains one line, directly under it, in this form:

> **STALE** -- recorded `<subject>` / now `<subject>`; re-measured `<date>`, `<what changed>`.

and if the state itself changed, the new state is added on that line with its own quoted token. The original line stays as it was: a map that is edited to look right stops being a record, for the same reason `decisions.md` leaves the `2.0087` copy standing.

**What a reader must do on hitting one:** treat the row as an unevidenced assertion -- which is what a stale row is -- and re-measure it before using it to justify anything. If the re-measurement is more than one command, the row was written wrong: section 0's rule (path + symbol, or path + quoted token) exists so that re-measurement is always one query.

**The third check, for the case the first cannot see.** If a path's subject still matches but the quoted token is gone from the file, the row is stale too. Grep the token. This covers what a commit-subject comparison cannot: a rebase, amend or history rewrite that leaves the graph's subjects equal while the file text moves.

**What is sustainable, and why.** There is **no review cadence**, and none may be added later. A map with "reviewed on <date>" and a six-month cadence is believed for five months and known-false for one, and in practice believed for all six; this repository's only scheduling mechanism is a dispatch, and dispatches are not periodic. So the trigger is an event: a dispatch that touches a mapped path re-measures the rows for the paths it touches, and a reader who needs a row checks it in one command. Staleness is a property of the row that the tree announces, not a duty someone remembers.

**The hole, stated rather than papered over.** This mechanism detects **edits to the thing described**, not **changes to the things that use it**. A component can become ACTIVE because a new front end imports it while its own path is untouched, and no row above would go stale. That case needs a reader; it cannot be mechanised from a per-path log. It is here, in the mechanism's own section, so that the first person to notice it does not conclude it was overlooked.

### The demonstration (one real row, rendered stale)

The row is the Route C report's **harness-side** copy -- the one that is easy to record wrongly, because it sits inside a directory that *is* tracked:

## Scope, and what this map does not claim

**In scope:** components -- the forty-odd modules, harnesses, front ends and documents above, grouped so that a reader finds one in five seconds.

**Out of scope as components:** `out/`, `study-out/`, `temp/`, `tmp_job2/`, `.scratch/`, `.venv/`, `.tools/`, `.thoughtmachine/` and the figure caches. They appear only where a finding requires an example (the unlanded rung-8 harness; the duplicated coupon project). An omission here is not a denial that the directory exists.

**Short fields, and they say so:** two rows (examples; the top-level M3-era diagnostics) carry no individual commit subject because the sweep did not query one. They are marked rather than filled with a neighbour's subject. Every other *verified* field was measured with a per-path log query this session.

**The map is frozen at this write.** It changes only by an appended **STALE** line as described above, or by an appended correction that names the row it corrects. It is not re-sorted, re-flowed or silently refreshed.
